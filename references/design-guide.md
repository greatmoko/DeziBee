# DeziBee 设计与数据规范

新建工作台入口为项目 index.html；已有项目使用其原有入口（例如 demo/index.html），WORKBENCH_DATA 必须使用严格 JSON（双引号、无注释、无模板字符串）。操作命令见 [工作台操作](workbench-operations.md)。

## 数据模型（唯一 ID 是核心）

```json
{
  "project": {
    "title": "示例需求"
  },
  "pages": [
    {
      "id": "page-overview",
      "name": "需求概述",
      "group": "",
      "prdId": "sec-overview",
      "cards": [
        {
          "id": "card-overview",
          "name": "需求概述",
          "x": 120,
          "y": 160,
          "w": 720,
          "h": 560,
          "shell": "browser",
          "status": "draft",
          "prdId": "sec-overview",
          "html": "<main><h1>示例需求</h1><p>版本：待补充</p></main>"
        }
      ]
    }
  ],
  "links": [],
  "prd": {
    "sections": [
      {
        "id": "sec-overview",
        "title": "1. 本次需求概述",
        "level": 2,
        "html": "<p>本次背景、目标与需求概述。</p>"
      }
    ]
  }
}
```

## 原型卡片（核心）

### 第一页：需求概述（固定）

- `pages[0]` 必须是「需求概述」页，必须放在所有具体业务页面之前。
- 需求概述页只展示本次原型的概要信息，不承载具体业务操作。
- 概述卡片通常展示：需求名称、版本信息、更新时间、需求状态、负责人等；没有确切信息时写「待补充」，不要编造。
- 具体业务页面从 `pages[1]` 开始创建；不要把首页、登录页等业务页面放在第一页取代需求概述页。
- 需求概述页对应的 PRD 章节放在 `prd.sections` 第一项，内容包括：本次需求背景和目标、需求概述；涉及跨页面流程时补充完整的文字流程说明，以及必要的其他概要信息。
- 后续 PRD 章节再按具体业务页面和原型卡片编写页面元素、交互和状态。

卡片 = 画布上的一个独立节点，字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| id | ✓ | 全局唯一，如 `card-login-default` |
| name | ✓ | 显示名 |
| type | 建议 | 自由定义：`page` / `dialog` / `state` / `flow` / `component`… |
| x, y | ✓ | 画布坐标（自由布局，注意留出间距 120+，给外壳留位） |
| w, h | ✓ | **屏幕内容区尺寸（CSS 像素 1:1）**，按设备实际尺寸定（见下表） |
| shell | 建议 | 系统外壳组件：`phone` 手机 / `tablet` 平板 / `browser` 浏览器；省略=无边框裸卡片 |
| status | 建议 | `draft` / `confirmed` / `deprecated`（可自由扩展） |
| prdId | ✓ | **关联的 PRD 章节 id（双向联动靠它，不要靠名称）** |
| html | ✓ | **真实 HTML/CSS/JS 原型。禁止用图片模拟页面** |

### 实际尺寸与外壳（重要，直接决定观感）

- **按设备真实 CSS 像素 1:1 生成**，不要缩小尺寸凑画布——画布可缩放平移，清晰度优先：
  - 手机竖屏页面：`w:375, h:812` + `shell:"phone"`（逻辑分辨率 iPhone 类）；
  - 平板竖屏页面：`w:820, h:1180` + `shell:"tablet"`；
  - 桌面/网页页面：`w:1440, h:900` + `shell:"browser"`（内容按 1440 设计）；
  - 弹窗/局部状态：跟随所属平台的尺寸（手机弹窗约 340×auto、桌面弹窗约 480×360），
    同平台统一用同一种 shell。
- `w/h` 始终指**屏幕内容区**；手机壳（圆角边框+刘海）、平板壳（窄边框）、
  浏览器壳（窗口顶栏+地址栏）由框架按 `shell` 自动绘制并适当扩展外围，
  你不需要也不应该用 HTML/CSS 画壳或画状态栏。
- 用户指定的设备类型是**默认壳**：新页面/页面级卡片默认用它；
  你仍可按卡片覆盖（如桌面 demo 里某张手机弹窗卡片用 `phone`）。
- shell 内容由你写满：手机页面内容按 375 宽设计、桌面页面按 1440 宽设计，
  **不要在 375 的壳里塞 1440 宽的桌面布局**（反之亦然）。
- **手机/平板安全区**：壳顶部有刘海/边框（手机约 54px、平板约 40px），
  页面第一个元素请加对应的 `padding-top`/`margin-top` 避开（如导航栏放其下），
  状态栏本身由外壳绘制，不要自己画时间/电量。
- **滚动条由框架处理**：原生滚动条已隐藏，页面滚动时右缘会浮现 3px 的浮动指示条
  （停止后自动消失）。不要自绘滚动条，也不要依赖滚动条宽度做布局。

`html` 写法要求：
- 只写 body 内片段（框架已包 iframe 文档）；样式可内联 `<style>`，脚本可用；
  不要写 `<html>/<body>` 外壳。
- 交互要真实可用：按钮能点、表单能填、弹窗能开（iframe 沙箱允许 scripts/forms/modals）。
- 页面级原型建议自带 `font-family:system-ui` 等基础样式；字体大小用真实设备
  逻辑像素（手机正文 14-16px、桌面正文 14px），勿因画布缩小而加大字号。

**什么值得成为独立卡片**（核心原则）：一个需要开发明确理解的独立视觉/交互状态。
例如：登录页默认态、登录页错误态、支付弹窗、下单成功页。

### 流程图卡片（type: flow）

用户提出需求后先判断是否需要流程图：涉及多个页面/步骤、多个角色或系统、判定分支、异常/回流、跨角色交接时需要；单页面、单状态或简单表单不需要。需要时先画流程图，再画原型。

布局与走线遵循 SKILL.md 的流程图规范：通常从上到下，尽量避免连线交叉和重叠。

流程图放在需求概述之后、业务页面之前，一页一张 `type: "flow"` 卡片。

**基本元素（简单流程）**

| 元素 | 形状 | 用途 |
|---|---|---|
| 开始/结束 | 胶囊（圆角矩形，圆角=高度/2） | 流程唯一入口和出口 |
| 节点 | 矩形 | 一个处理步骤 |
| 判定 | 菱形 | 条件分支，出口标注「是/否」或具体条件 |
| 子流程 | 左右带双竖线的矩形 | 可展开的子步骤集合 |
| 输入/输出 | 平行四边形 | 读取或输出数据 |
| 连接线 | 带箭头实线 | 步骤之间的流转方向 |

**简单流程**

- 单角色、无跨角色交接、节点较少时使用。
- 只画一条主泳道，按从上到下或从左到右排列；异常和回流用侧向分支和回退箭头表示。
- 判定分支必须有标签；开始/结束各一个；节点名称与原型状态一致。
- 建议卡片 `w: 1100, h: 720`，不加设备壳。

**复杂流程**

- 多角色、多系统、多阶段或存在跨角色/跨系统交接时使用。
- 泳道 + 上述基本元素：每条泳道代表一个角色/系统/阶段，泳道标题在左侧；节点放在执行该步骤的泳道内。
- 跨泳道交接用箭头连接，箭头标签写清动作或数据；同一泳道内可用竖向流程线。
- 泳道数量多时可加宽卡片（如 1200×800），保持节点和连线不交叉、不重叠。
- 判定、异常、回流规则与简单流程一致。

**通用规则**

- 流程图必须与 pages/cards/links 一致；新增或删除状态时同步更新流程图节点和连线。
- 流程图只做汇总，字段规则、异常和 API 仍写在对应页面/卡片章节，不重复。
- 用真实 HTML/SVG 绘制，禁止截图；主流程、可选/异常分支、未实现步骤用颜色或线型区分，并在图例中说明。

## PRD 章节

- PRD 第 1 章固定对应第 1 个画布「需求概述」，用于说明本次迭代的背景、目标、需求概述和必要的全流程文字说明；保持简短，不写成完整项目文档。第 1 章下可以有 1.1 卡片章节（如需求概述卡片）。
- 从第 2 个画布开始，按画布顺序组织：每个画布是一级章节，画布内的每张原型卡片是二级章节；只覆盖本次迭代实际涉及的内容。
- 需求很小时，画布章节和卡片章节即可，不要强行添加接口、权限、埋点、性能等无关章节。
- 每个**卡片**必须有对应二级章节（`card.prdId` → `section.id`），在章节里表达：
  页面设计 / 结构 / 功能 / 元素 / 交互 / 页面跳转；按实际需要补充状态、异常或业务规则。
- 每个画布的页面级说明写在画布一级章节内，按以下顺序组织；不适用的项可以省略，用户也可以要求 AI 补充其他开发所需信息：
  1. 业务需求概述
  2. 页面结构
  3. 元素说明（按区域描述整个页面；每个区域包含展示组件、字段、功能按钮等信息）
  4. 业务规则（前端规则 + 后台规则：校验、约束、状态变更、权限、幂等、频率限制、数据一致性、审计等）
  5. 数据/API
  6. 报错及异常
- 业务规则必须区分**前端规则**和**后台规则**。前端规则写交互、校验提示、跳转和展示；后台规则写服务端校验、字段约束、状态变更、权限、幂等、频率限制、数据一致性和审计。后台规则是最终判定依据；未知的阈值、错误码、接口字段写「待补充」，不要编造。
- **自动编号规则**：画布（页面）是 PRD 一级章节，画布内的原型卡片是二级章节。例如画布 3「Informasi Pribadi」下的卡片依次为 3.1、3.2…；卡片内的说明用三级编号 3.1.1、3.1.2…。新增内容继续顺延，不重置、不跳号。
- 画布章节内部的页面级说明使用不带编号的 h3 小标题，避免与卡片编号 3.1、3.2 冲突；卡片章节内部再用 3.1.1、3.1.2 编号。
- `section.level`：画布章节填 1，卡片章节填 2；画布章节标题写成 `3. 页面名`，卡片章节标题写成 `3.1 卡片名`。
- 编号只按 PRD 文档顺序和章节层级计算，不使用页面名称、卡片名称或 ID 代替编号；修改已有 PRD 时保留未修改章节的编号，新增章节插入后顺延后续编号。
- 每个画布必须有画布级章节（`page.prdId` → `section.id`）；画布内每张卡片有二级章节（`card.prdId` → `section.id`）。进入画布时默认选中第一张卡片并定位其章节；第一张卡片没有关联章节时定位画布章节。单击卡片标题时定位到对应二级章节。
- 无卡片的画布级说明也可以加纯章节（不需要 prdId 对应）。
- 章节 `html` 中引用某张卡片时，用原型引用标签（点击 → 画布聚焦该卡片）：

```html
参见 <span class="prd-ref" data-card-ref="card-login-default">登录页原型</span>
```

- 也可以用 `<a href="#sec-章节id">` 做章节内跳转（框架给每个章节容器加了
  `id="sec-<章节id>"` 前缀，注意 `#sec-` 前缀要带上）。

## 双向关联（必须遵守）

- 页面 → PRD：左栏**切换页面** → 默认选中第一张卡片，右栏定位其关联章节；无关联时定位画布章节。
- 卡片 → PRD：浏览器里**单击卡片标题选中卡片** → PRD 自动滚动到对应章节并高亮。
- PRD → 卡片：点击章节里的 `data-card-ref` 引用 → 画布切到所属页面并聚焦高亮卡片。
- 关联全靠 `id`（`card.prdId` / `data-card-ref`）。**禁止**依赖名称匹配。

## 连线与状态关系（links）

同一页面内的卡片用 `links` 表达状态流转。画布会绘制带箭头的贝塞尔曲线，曲线中点显示说明文字；悬停显示触发条件与补充说明；点击线会聚焦目标卡片并联动 PRD。

```json
"links": [
  {
    "id": "link-default-picker",
    "from": "card-personal-default",
    "to": "card-personal-picker",
    "trigger": "点击 Jenis Kelamin",
    "condition": "字段可编辑",
    "note": "选择后回显并关闭底部选择器"
  }
]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 建议 | 全局唯一；用于调试和后续修改 |
| `from` | ✓ | 起点卡片 id，必须真实存在 |
| `to` | ✓ | 终点卡片 id，必须真实存在 |
| `trigger` | 建议 | 曲线中点的短标签，建议 6–14 个字符，写清“什么操作” |
| `condition` | 否 | 触发条件；悬停时与 trigger、note 一起展示 |
| `note` | 否 | 补充说明；没有 trigger 时作为中点标签 |
| `label` | 否 | trigger 的别名，优先级最高 |

规则：

- 同一页面内存在多个状态卡片时，**必须**用 links 标出状态之间的流转，不能只摆卡片不画关系。
- 每条线都要有可读的说明（trigger 或 label），禁止无标签连线。
- 只连接同一页面内真实存在的卡片；跨页流程写在 PRD 的流程说明里，不要建跨页线。
- 连线不替代卡片内交互：卡片 iframe 内的点击、弹窗仍由卡片自身实现。
- 删除卡片时同步删除以它为 from/to 的 links；修改卡片 id 时同步更新。
- 同一对卡片只建一条线；双向关系用两条线并在 label 中写清方向。

## 画布操作（给用户看的提示）

- 拖空白处平移；滚轮缩放；双击空白=适应全部内容
- `0` 回原点；`Ctrl+1` 全局适应内容；`Esc` 取消选中
- 卡片头部可拖动移动位置；工具栏「◎ 聚焦」聚焦选中卡片
- **PRD 宽度**：拖动中栏与右栏之间的竖直拖拽条可调整宽窄（双击复位）；宽度会本地记忆
- **PRD 编辑区高度**：编辑态下拖动正文框下方的小横条可加高/收窄（高度会本地记忆）
  —— 这两项纯属展示偏好，不改数据，AI 无需处理。

## 页面管理（AI 对话驱动）

用户新增/删除/重命名/排序页面时，修改 `pages` 数组：
- 新增：`pages.push({...})` 的数据形式（即编辑 index.html 中的数组文本）
- 删除：从数组移除；**同时**清理其卡片的 links 与对应 PRD 章节，避免死链
- 重命名：改 `name`（id 不变，关联不断）
- 排序：调整 `pages` 数组顺序；导航严格按数组顺序渲染，分组名称不参与排序。同组页面需要连续展示时，将它们放在数组的相邻位置。
- 关联页面的 PRD 章节按对应页面在 `pages` 中的顺序组织，不按页面或分组名称另行排序。
